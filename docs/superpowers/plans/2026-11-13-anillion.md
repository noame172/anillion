# Anillion Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A launch-ready daily anime guessing game where rarer valid answers score more and a hero powers up with the total score.

**Architecture:** One Next.js App Router project. Pages are thin; all game rules live in pure modules under `src/lib/game`, and all reads/writes go through server route handlers using a server-only SQL client. The SQL client has two drivers behind one interface: `pg` (Supabase Postgres, production) and PGlite (embedded Postgres, dev mode without keys), both running the same migrations.

**Tech Stack:** Next.js 15, React 19, TypeScript (strict), zod, `pg`, `@electric-sql/pglite`, `@supabase/ssr` + `@supabase/supabase-js`, `jose` (signed cookies), vitest, plain CSS modules.

**Spec:** `docs/superpowers/specs/2026-11-13-anillion-design.md`

## Global Constraints

- Tier points are exactly: common 25, rare 50, epic 75, ultra 100.
- Hero form by total score: base 0-199, ascended 200-349, azure 350-499, ultra 500+.
- Default rarity thresholds (share of valid submissions): common > 10%, rare > 3% and <= 10%, epic > 1% and <= 3%, ultra <= 1%. Configurable.
- Minimum sample before automatic rarity: 100 valid submissions per question. Configurable.
- Default 7 questions per daily game. Configurable.
- Each question has a 30-second server-enforced timer. Wrong answers do not count and can be retried freely until time runs out; the first valid answer scores and locks the question; a timeout scores 0. (User ruling 2026-11-13: replaces the 3-attempt limit and Skip button; `answer_attempts` table and `maxAttempts` are dropped, `submissions.skipped` becomes `timed_out`, sessions gain `current_started_at`, and a `POST /api/game/next` call starts the next question's timer.)
- Rarity is frozen per daily game at publish time; the current day's submissions only feed future games.
- An answer is valid only if it matches an approved answer or alias in the database.
- Score, tier, share, user id and role are never read from the client.
- All timestamps stored in UTC (`timestamptz`); the game date comes from server time + configured timezone and rollover hour.
- No secrets in client bundles; only `NEXT_PUBLIC_*` variables reach the browser.
- Optional integrations (AniList, AI helper, AdSense, Analytics) do nothing unless their env vars are set.
- Original visual identity and hero; no third-party artwork in the repo.

## Review Focus

1. Two requests answering the same question at once (double click, two tabs): exactly one submission row and one score increment. Test in Task 5.
2. Answer text with accents, punctuation, full-width characters or 500+ characters: normalised or rejected cleanly, never a 500. Test in Task 3.
3. A request arriving seconds after rollover for yesterday's unfinished session: it is rejected with a clear "game ended" message, not scored into today. Test in Task 5.
4. A question with zero prior submissions or an answer approved after publish: scored with the provisional tier, share shown as "new". Test in Task 4.
5. A guest who finishes today's game, then registers: the session moves to the account once, and the account cannot replay. Test in Task 7.

### Task 4: Settings, validation, rarity snapshot, daily game

**Files:** `src/lib/settings.ts`, `src/lib/game/validate.ts`, `rarity.ts`, `daily.ts`, `tests/validate.test.ts`, `rarity.test.ts`, `daily.test.ts`

**Interfaces — Produces:**
- `getSettings(): Promise<Settings>`; `Settings = { thresholds: Thresholds; minSample: number; questionsPerGame: number; timezone: string; rolloverHour: number; maxAttempts: number; autoGenerate: boolean }`. Defaults: thresholds above, 100, 10, `'UTC'`, 0, 3, true. `updateSettings(patch)` validates with zod.
- `matchAnswer(questionId: string, raw: string): Promise<{ answerId: string; canonical: string } | null>` — matches `answers.norm` or `answer_aliases.norm`, verified answers only.
- `recordUnknown(questionId: string, raw: string): Promise<void>`
- `buildSnapshot(q, gameId: string): Promise<void>` — per question: total = sum of `valid_count`; if total ≥ minSample, share = count/total·100 and tier = `tierForShare`; otherwise share null, tier = `provisional_tier`, provisional true.
- `lookupRarity(gameId, questionId, answerId): Promise<{ tier: Tier; share: number | null; provisional: boolean }>` — falls back to the answer's provisional tier when no snapshot row exists.
- `gameDateFor(now: Date, timezone: string, rolloverHour: number): string` (`YYYY-MM-DD`); `nextRolloverAt(now, timezone, rolloverHour): Date`
- `getTodayGame(now?: Date): Promise<DailyGame | null>` — returns the published game for the date; if none and `autoGenerate`, creates one from the least recently used active questions, snapshots it and publishes it (inside a transaction, safe under concurrent calls via the `game_date` unique constraint).
- `publishGame(gameId): Promise<void>` — stores `config_snapshot`, calls `buildSnapshot`.

- [ ] Tests: aliases and case/whitespace variants match the same `answerId`; an answer from another question does not match; unverified answers do not match; snapshot with 200 submissions (90/20/10/2 split etc.) yields expected tiers; snapshot with 50 submissions uses provisional tiers; stats added after publish do not change `lookupRarity`; `gameDateFor` across the rollover boundary in `Asia/Jerusalem` with rollover hour 5; two concurrent `getTodayGame` calls return the same game id.

### Task 5: Sessions, submissions, streaks

**Files:** `src/lib/game/session.ts`, `streak.ts`, `tests/session.test.ts`, `streak.test.ts`

**Interfaces — Consumes:** Task 3 and 4 exports. **Produces:**
- `type Viewer = { kind: 'user'; id: string; role: 'user' | 'admin' } | { kind: 'guest'; id: string }`
- `startSession(viewer: Viewer): Promise<GameState>` — idempotent per viewer and game.
- `getState(viewer: Viewer): Promise<GameState | null>`
- `submitAnswer(viewer: Viewer, input: { questionId: string; text?: string; skip?: boolean }): Promise<SubmitResult>`
- `SubmitResult = { status: 'accepted'; canonical; tier; points; share; provisional; state: GameState } | { status: 'unrecognised'; attemptsLeft: number } | { status: 'skipped'; state: GameState }`
- `GameState = { date; position; total; score; form; progress; current: { id; text; category } | null; answers: AnsweredRow[]; completed: boolean; nextGameAt: string }` — never includes unanswered questions beyond the current one.
- `nextStreak(prev: { streak: number; lastPlayed: string | null }, today: string): number`

Rules: only the current question (lowest unanswered position) can be answered; errors `NOT_CURRENT_QUESTION`, `GAME_OVER`, `GAME_ENDED` (session belongs to a past date), `ALREADY_ANSWERED`. An unrecognised answer increments `answer_attempts`; when attempts reach `maxAttempts` the question is closed with 0 points. Accepting an answer, updating `total_score`, `answer_stats` and (on completion) profile totals/streak happen in one transaction with `select ... for update` on the session row.

- [ ] Tests: full 10-question run totals match tier points; form changes 175 → 275 gives `ascended`; duplicate submit for an answered question is rejected and score is unchanged; two concurrent submits produce one row; submitting question 3 while on question 1 is rejected; third unrecognised attempt closes the question at 0; second `startSession` returns the same session and a completed session cannot restart; session from yesterday returns `GAME_ENDED`; streak 3 → 4 on consecutive day, resets to 1 after a gap, unchanged on same day.
- [ ] Implement, run, commit.

### Task 6: Auth, guest identity, rate limits

**Files:** `src/lib/auth/*`, `src/lib/security/*`, `src/middleware.ts`, `src/app/api/auth/**`, `tests/auth.test.ts`, `ratelimit.test.ts`

**Interfaces — Produces:**
- `getViewer(): Promise<Viewer>` — user from Supabase session (verified with `auth.getUser()`) or, in dev-local, from a `jose`-signed httpOnly cookie; otherwise a guest id from a signed httpOnly cookie (created on first use). Role and suspension always read from `profiles`.
- `requireUser()`, `requireAdmin()` — throw `HttpError(401 | 403)`.
- `rateLimit(key: string, limit: number, windowSec: number): Promise<void>` — DB-backed fixed window, throws `HttpError(429)`.
- `assertSameOrigin(req)` — rejects state-changing requests whose `Origin` does not match the host.
- `apiHandler(fn)` — wraps route handlers: zod parsing, `HttpError` → JSON, unknown errors → generic 500 with logged detail.
- Dev-local auth routes: register, login, logout, change password; passwords hashed with `scrypt` + per-user salt. Supabase mode: sign-up with email verification, login, logout, reset password, update password via `@supabase/ssr`.
- Limits: login 5 / 15 min per IP+email; register 5 / hour per IP; answer 30 / min per viewer.
- Username: 3-20 chars, `[A-Za-z0-9_]`, unique case-insensitively.
- Account deletion: deletes profile and credentials; sessions are anonymised (user_id null, guest_id set to a random id).

- [ ] Tests: 6th login attempt in the window → 429; wrong password → 401 without revealing whether the email exists; `requireAdmin` rejects a `user` role and a guest; forged/unsigned cookie is treated as a guest; cross-origin POST is rejected.
